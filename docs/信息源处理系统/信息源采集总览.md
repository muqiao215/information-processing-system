# 信息源采集总览

## 标准文件

- [[README]]：目录入口和分层口径。
- [[信息源注册表]]：当前 canonical registry。
- [[信息源契约模板]]：新增或改造信息源时使用的字段模板。

## 一句话判断

当前定时任务里的“收集信息”并不只是 `RSS + Jina + 博客` 三类。
更准确的分法是按 **信息源契约** 来看：

1. 固定 feed / 聚合 feed
2. GitHub 页面或 GitHub 数据面
3. 仓库即内容归档
4. 学术 API
5. 下游合成与产物生成
6. 运维遥测（不属于内容信息源）

也就是说，真正重要的不是“是不是 RSS”，而是：

- 上游是谁
- 访问路径是什么
- 输出是不是稳定的 Markdown / JSON manifest
- 这个任务是在“采集”，还是在“加工”

## 按来源机制归类

### 1. 聚合 feed 型

这类任务的特点是：上游已经帮你做过一次汇总，任务本身负责再筛选、再重组、再产出面向你的简报。

#### `follow-builders`

- 关联 cron: `ai-builders-digest-5briefs`
- 本地 skill: `/root/.controlmesh/workspace/skills/follow-builders`
- 私有同步源: `/root/private-sync-bundle/skills-selected/follow-builders`
- 上游内容类型:
  - X / Twitter builders
  - YouTube 播客
  - 博客
- 当前定位:
  - 主 digest 的主链
  - 负责生成 A-E 五栏
  - 负责写下游 NotebookLM 要吃的 source manifest

判断：这是“聚合 feed -> 人工风格二次编排 -> 结构化 manifest”的标准主链。

### 2. GitHub 数据面 / 页面型

这类任务不是典型 RSS，而是直接把 GitHub 当作信息源本体。

#### `daily-github-trending-ai-watch`

- 信息源: GitHub Trending
- 工具路径: 自带脚本抓取
- 输出: Top 8 + 最值得看的 4 个
- 本质: 日榜监控器

#### `daily-news-summary-7am`

- 其中 CLI 更新部分：
  - Claude Code release
  - OpenAI Codex CLI release
- 这部分的信息源其实也是 GitHub release page

判断：这两条都不该归到“普通 RSS”，更接近“平台原生数据面 / 正文页读取”。

### 3. 仓库即内容归档型

这是现在最值得单独分出来的一类。

#### `BuilderPulse/BuilderPulse`

- 本地路径: `/root/.controlmesh/workspace/vendor/BuilderPulse`
- 上游仓库: `BuilderPulse/BuilderPulse`
- 关联 cron: `daily-builderpulse-opportunity-radar`
- 内容结构:
  - `zh/YYYY/YYYY-MM-DD.md`
  - `en/YYYY/YYYY-MM-DD.md`
- 当前定位:
  - 独立情报源
  - 主打 builder demand / opportunity radar
  - 不并入现有主 digest，而是单独产出 `F. 机会雷达`

判断：这不是 skill，也不是 RSS。
它更像“用 Git 仓库存放每日内容快照”的内容归档源。

### 4. 学术 API 型

#### `arxiv-llm-memory-discovery`

- 关联 cron: `daily-arxiv-llm-memory-discovery`
- 本地 skill: `/root/.controlmesh/workspace/skills/arxiv-llm-memory-discovery`
- Hermes live copy:
  `/root/.controlmesh/workspace/vendor/hermes-agent/.hermes-home/skills/research/arxiv-llm-memory-discovery`
- 私有同步源:
  `/root/private-sync-bundle/skills-selected/arxiv-llm-memory-discovery`
- 信息源: arXiv API
- 查询方式: `abs:` scoped query
- 过滤目标:
  - LLM memory
  - long-term memory
  - context window / KV cache
  - RAG-style memory augmentation
  - semantic / episodic memory
- 明确排除:
  - Mamba / state-space
  - time-series
  - memory-efficient training / GPU memory 噪声

判断：这是非常典型的“API 查询 -> 相关性过滤 -> 单条高信号推送”。

### 5. 下游合成 / 产物型

这类任务经常和采集任务混在一起看，但本质不同。

#### `daily-notebooklm-content-gen`

- 输入: `ai_builders_digest_sources_latest.json`
- 输出: NotebookLM report
- 角色: 二次合成

#### `daily-notebooklm-artifact-trigger`

- 输入: report run metadata
- 输出: slide / video generation trigger
- 角色: 产物派生

判断：这两条不应该归到“信息源采集”，而应该归到“基于信息源的下游生成链”。

## 技能 vs 仓库

### 属于 skill 的

- `follow-builders`
- `arxiv-llm-memory-discovery`

特点：

- 有明确的 skill 目录
- 可同步到私有 skill bundle
- 可被 Hermes / workspace / 本地脚本复用

### 属于独立仓库的

- `BuilderPulse/BuilderPulse`

特点：

- 它自己就是内容载体
- 没有 `SKILL.md`
- 不是执行逻辑，而是上游内容仓

### 属于独立 cron task 逻辑的

- `daily-news-summary-7am`
- `daily-github-trending-ai-watch`
- `daily-notebooklm-content-gen`
- `daily-notebooklm-artifact-trigger`

特点：

- 逻辑主要写在 `cron_tasks/<job>/TASK_DESCRIPTION.md` 与配套脚本里
- 不一定需要抽成 skill

## 当前最有用的分类结论

如果只做一版最实用的归类，可以直接记成下面这张表：

| 类别 | 代表项 | 典型来源 |
| --- | --- | --- |
| 聚合 feed | `follow-builders` | X / podcast / blog |
| GitHub 数据面 | `daily-github-trending-ai-watch` | GitHub Trending |
| GitHub 正文页 | `daily-news-summary-7am` 的 CLI 更新段 | GitHub releases |
| 仓库归档源 | `BuilderPulse/BuilderPulse` | 每日 markdown archive |
| 学术 API | `arxiv-llm-memory-discovery` | arXiv API |
| 下游合成 | NotebookLM 两条 cron | NotebookLM |
| 运维遥测 | quota / health check cron | 配额与服务状态，不算内容源 |

## 后续整理建议

如果后面继续收口，我建议把“信息源采集”统一看成三层：

1. source collector
2. selector / ranker
3. synthesizer / artifact generator

然后所有任务都统一补一份最小 manifest 字段：

- `source_type`
- `source_of_truth`
- `access_path`
- `selected_items`
- `output_files`
- `failure_mode`

这样以后你看一眼就知道：
到底它是在抓源、选源，还是在做下游生成。
